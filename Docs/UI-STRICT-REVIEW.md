# Strict player-facing UI review

Review date: 10 October 2026
Scope: every player-facing UI surface found in the current Unity runtime, from first launch through town, collection, combat, reconnect, rewards and exit paths. Revisions 95–97 update the Events list/detail source; runtime compilation and visual review remain pending Unity Editor/license access.

## Evidence and limits

This review traced the active screen-building and interaction code in `SplashScreenUI`, `CharacterCreatorUI`, `TownHubManager`, `InventoryModal`, `SkillWheelHUD`, `ExpeditionHUD`, `EventDrawerUI`, `InboxDrawerUI`, `PauseManager`, `ArenaGame`, `CoopSession` and `LeaderboardModal`. It also compared those flows with the earlier two-pass reference inventory in [MYHEROES-UI-AUDIT.md](MYHEROES-UI-AUDIT.md), the five sampled gameplay-video register in [MYHEROES-GAMEPLAY-REFERENCES.md](MYHEROES-GAMEPLAY-REFERENCES.md), prior local UI captures and the screenshots supplied by the user.

The comparison set includes [My Heroes: SEA gameplay](https://www.youtube.com/watch?v=9k_rK9_oSio), [My Heroes: Dungeon Raid gameplay](https://www.youtube.com/watch?v=gLHw_H5kPi8), the [My Heroes Quests UI wiki](https://myheroesofficial.fandom.com/wiki/Quests_(UI)), and [Skills information](https://myheroesofficial.fandom.com/wiki/Skills_(Information)). My Heroes uses compact corner anchors in combat, explicit lobby navigation, a paperdoll beside the item grid, and a separate item-detail layer. The wiki supports Adventure/Diary/Goals quest navigation and distinguishes skill books and their progression. It does not establish every hidden interaction or every commercial screen. Existing notes record two-pass rechecks of the referenced combat, shop, backpack and item-detail frames; they do not claim a complete playthrough or parity with unobserved screens.

This is a source-level review anchored to existing recorded captures, not a fresh hands-on pass through every transient runtime state or a current Android-device capture. Findings about code structure and visible controls are direct; findings about tap difficulty, focus and visual overlap need the listed device acceptance. Where the reference evidence does not cover an equivalent My Heroes page, that is called out instead of guessed.

## Executive assessment

The issue is hierarchy, not a lack of polish. The game currently exposes controls at the same time as places, modes, currencies, item filters, sort, pages, actions and status. Several screens use the same visual weight for primary and secondary actions. The result is a UI that looks like a collection of individually added buttons instead of a deliberate journey with one obvious next action.

The closest reference match is the broad two-column backpack silhouette. The largest differences are the town navigation, first-run account flow, the missing dedicated skill-loadout page, incomplete paperdoll slots, overloaded combat edge, and result screens that do not make the reward/next action the hero. The My Heroes footage shows compact, stable edge groups around a clear playfield; our implementation imitates the edge positions but does not yet achieve the same reduction and consistency.

## Common interaction and layout defects

1. **Multiple navigation models:** world signs, screen-positioned buttons, keyboard shortcuts, modal tabs and action buttons all navigate the same areas. Choose one primary navigation model and make shortcuts alternate inputs to the same destinations.
2. **No single primary action:** registration, town, events, inventory, settings and result layers often give every button the same visual weight. Each page needs one primary CTA, then lower-emphasis secondary actions.
3. **Duplicate dismissal:** event/inbox screens have X and Close; item inspection layers have their own close over a collection that already has close. Keep one consistent close affordance per layer, plus platform Back/Escape.
4. **Fixed 1280×720 authoring:** most interfaces use absolute coordinates around a 1280×720 reference canvas. Safe-area support exists, but it does not by itself reflow multi-column layouts for a narrow phone or accommodate every camera cutout. The 1280×720 visual reference was designed landscape; portrait behavior is unproven.
5. **Feedback split across layers:** rewards and errors are written into gameplay status text while a separate canvas shows only the next button. State, consequence and next step must be visible together.
6. **Reference imitation without reference hierarchy:** dark violet frames, pixel icons and bright borders are present, but matching colors does not reproduce the stable lobby rails, compact information density and obvious next action visible in My Heroes.

## Recommended redesign order

1. **Lock the screen map before drawing more buttons.** Define three top-level destinations: Adventure (town/modes/quests/events), Hero (equipment and skills), and Account/Settings. Use one persistent currency/identity header and one consistent modal/back rule. Gate unavailable modes in place.
2. **Fix first-run flow.** Default to sign-in; create account and recovery become explicit secondary routes. Remove the extra Enter step when there is no saved session. Make account completion and character creation separate, focused stages.
3. **Make town useful at a glance.** One highlighted Campaign action, grouped utility navigation, in-world merchant labels only at proximity, clear event/claim badges tied to real states, no duplicate Interact button when a contextual tap is available.
4. **Restore the hero and skill hierarchy.** Larger paperdoll, truthful current three-slot gear until the six-slot data migration ships, dedicated skill assignment after its active-slot migration. Do not paint locked/inert controls as usable.
5. **Reduce combat competition.** Keep stable edge anchors, increase touch spacing, show only essential objective/map/ally information, give the attack and live boss the strongest game-state emphasis, and test the actual phone aspect/safe areas.
6. **Redesign event, inbox and item details around outcomes.** Event = objective/reward/time/Go; item = identity/current-vs-new/one action; inbox = clear reward and delivered confirmation.
7. **Make results tell the story.** Put earned rewards, stage outcome and one next action in the same visible result panel. Make retries describe exactly what has or has not been saved.
8. **Review all flows in the running client.** Capture sign-in, create/recover, town, bag, shop, item details, skills, settings/account/sign-out confirm, events/list/detail/claim, combat, pause, room clear, defeat, reconnect and leaderboard at 1280×720, 1024×768, 19.5:9 Android landscape, a cutout device and keyboard/controller input. A code review is not visual acceptance.

## Acceptance bar for the next UI implementation

- First-time player can reach play without guessing whether to tap Enter, Sign in or Register.
- At most one clearly emphasized primary action on each page; secondary controls are grouped and visually quieter.
- Top-level destinations remain in the same place. A player can return with one consistent Back action.
- No town/sign controls overlap player, gates, wallet or navigation at supported landscape safe areas.
- Combat keeps its center open and all touch targets clear at phone scale; boss name/health, player health, main attack and active skills remain distinguishable under heavy VFX.
- Event, reward, item and defeat states show their explanation, consequence and next action together.
- No invisible scroll overflow: event, inbox and leaderboard lists expose scrolling or pagination when needed.
- My Heroes-inspired structures use our own art and truthful game systems. Unverified source behavior is not described as parity.
- Desktop and Android build checks, UI boundary tests and screenshot review pass. A human first-time-player test completes onboarding, equips an item, assigns skills, finds an event and returns from combat without coaching.
